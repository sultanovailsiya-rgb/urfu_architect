# ДЗ «Архитектура проекта» — план работы

**Задание:** разработать архитектуру проекта (6 задач, 100 баллов).
**Выбран вариант:** Вариант 1 — учебный кейс «видеохостинг».

## Почему вариант 1, а не свой проект

- Задачи 1–2 уже расписаны списками действий (7 историй владельца + 7 историй зрителя) — остаётся оформить их в формат «Как … я хочу … чтобы …» и добавить критерии приёмки. Минимум творчества, минимум риска, что преподаватель увидит «не то».
- Вариант 2 (собственный проект) требует самой определять акторов и писать портреты пользователей для каждой роли — объём больше, а оценка субъективнее.
- Задачи 3–6 в обоих вариантах делаются одинаково, значит весь выигрыш — в задачах 1–2, и там вариант 1 строго проще.
- Предметная область знакома (аналог YouTube): легко обосновывать нефункциональные требования и рисовать процесс загрузки.

## Что делаем по каждой задаче

### Задачи 1–2 (20 баллов) — текст
Формат истории: «Как <роль>, я хочу <действие>, чтобы <цель>».
Критерии приёмки — списком «дано / когда / тогда» простыми фразами: что видит пользователь, что происходит в системе, что при ошибке. Обязательно ошибочные сценарии: неверный пароль, дубль регистрации, неподходящий формат файла, удаление чужого комментария, отмена лайка и т.п.

### Задача 3 (30 баллов) — самая весомая из текстовых
Планирую 4 требования (с запасом над минимумом в 2):
1. **Масштабируемость и производительность** — цель «20% видеотрафика РФ» означает пики вечернего трафика: старт воспроизведения ≤ 2 с (P95), горизонтальное масштабирование, CDN.
2. **Доступность (availability)** — 99,9%: простой = потеря просмотров и выручки в сторону цели 86 млн ₽.
3. **Безопасность и защита персональных данных** — регистрация и вход (152-ФЗ), права доступа к видео (владелец управляет, зритель — нет), защита от неавторизованных действий.
4. **Точность учёта статистики и выплат** — просмотры/лайки напрямую влияют на выплаты владельцам: идемпотентность, защита от накрутки.

Каждое требование: формулировка → метрика → обоснование (к какую стратегическую цель или бизнес-риск привязано).

### Задача 4 (30 баллов) — BPMN (навык bpmn-diagrams)
Процесс «Загрузка видео владельцем». Дорожки: Владелец видео | Веб-приложение | Сервис обработки видео | Хранилище и БД.
Шаги: вход в ЛК → создание загрузки → выбор файла → проверка формата и размера (шлюз: да / нет → сообщение об ошибке → повтор) → передача файла → транскодинг → генерация превью → ввод названия и описания → выбор режима публикации → публикация → уведомление владельца.
Результат: .bpmn + PNG, картинка проверяется перед сдачей.

### Задачи 5–6 (20 баллов) — PlantUML
- **Компоненты:** веб/мобильный клиент, API Gateway, сервис авторизации, сервис управления видео, сервис транскодинга, поисковый сервис, сервис комментариев и лайков, сервис статистики и выплат; БД метаданных, объектное хранилище (видеофайлы), CDN.
- **Развёртывание:** узлы — клиент (браузер/мобильное приложение), CDN, балансировщик, кластер прикладных серверов, кластер воркеров транскодинга, СУБД (мастер + реплика), объектное хранилище, мониторинг и логи.

## Формат сдачи
- Один документ (.docx): задачи 1–3 текстом, диаграммы 4–6 встроены.
- Отдельно PNG всех трёх диаграмм; рядом исходники (.bpmn, .puml) — чтобы можно было поправить по замечаниям.
- Ни одного упоминания ИИ; текст — от первого лица, женский род; перед сдачей — anti-ai-check.

## Порядок работы (фазы)
1. Задачи 1–2 — тексты историй и критериев приёмки.
2. Задача 3 — НФТ с обоснованиями.
3. Задача 4 — BPMN → PNG.
4. Задачи 5–6 — PlantUML → PNG.
5. Сборка .docx, вычитка, anti-ai-check, git init + коммит. Отправка — по подтверждению.

## Открытый вопрос
В задании есть ссылка на «подробное описание видеохостинга» (его нефункциональные требования и описание бизнеса) — в текст она не вставилась, в открытой сети не нашлась. Если файл или ссылка есть — пришли: от него могут зависеть детали НФТ и шаги процесса (форматы файлов, модерация, монетизация и выплаты). Без него опираюсь на функции из задач 1–2 и стратегические цели.
